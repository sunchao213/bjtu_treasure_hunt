### 四份交付物的责任边界

1. **需求文档（冻结）**：A 维护总稿；B/C/D 分别提供数据、战斗场景、UI 需求；E 检查每条需求是否有验收用例。冻结后只允许通过《修改说明》记录变更。
2. **概要与详细设计文档**：B、C、D 各写负责模块，A 统一架构图、模块接口和编号；E 检查设计是否可测试、是否与代码一致。
3. **修改说明**：每次修改必须写明“原内容—修改后—修改原因—影响范围—验证结果—责任人”。A 汇总，E 复核证据。
4. **第 9–15 周项目计划**：A 维护总甘特/周计划；每名成员填写本人的任务、产出、前置依赖和完成标准。第 14 周安排验收，第 15 周只做答辩材料和问题修复。

### 提交前自查顺序

E 先按需求编号逐条执行验收用例并记录结果；B/C/D 对照各自模块修正文档和实现；A 冻结版本号、合并《修改说明》并做最终一致性检查。提交包至少包含四份文档、测试用例及结果、修改说明、项目计划和必要的运行截图/构建记录。

上述测试执行与证据留存为建议质量措施；本次截图明确要求的是设计验收用例，尚未执行的用例必须标记“待执行”，不可写成通过。

## 角色与模块归属

### 1. 战斗与场景层

负责文件：`src/scenes/world-scene.ts`、夜间战斗与光照、`combat-config.ts` 等战斗相关模块。

- 第一轮：装备栏接入战斗结算、敌人掉落生成。
- 第二轮：玩家四方向雪碧图替换色块角色、Y-sort 深度排序改造。
- 第三轮：性能调优、战斗回归修复。

### 2. 数据与规则层

负责文件：`items.ts`、`inventory-service.ts`、`save-system.ts`、loot/raid 服务、`quest-service.ts`、`chapter-content.ts`。

- 第一轮：装备栏数据结构定义、分区域掉落表、物品实际用途、存档兼容检查。
- 第二轮：两条新任务链（围绕 `siyuan-key`、`anomalous-embrace-token`）、难度选项、新章节内容。
- 第三轮：数值平衡调整。

### 3. UI 与交互层

负责文件：`reference-shell.ts`、`main.ts`、`style.css`、`src/modules/ui/`。

- 第一轮：视图拆分（主页大厅、行前准备、仓库/图鉴、设置）、移动端适配。
- 第二轮：难度选项界面、任务链界面呈现、图鉴展示。
- 第三轮：修复试用反馈中的界面类问题。

### 4. 测试与质量

横切所有模块，不专属文件。

- 第一轮：补齐 `npm run check` 关键路径单测（存档加载、战斗结算、掉落生成）、真机 iOS/Android 测试规程、部署基线确认。
- 第二轮：组织集成测试与系统测试（对齐课程第 11/12 周）、设计 50 人试用反馈收集渠道。
- 第三轮：主导性能测试（Phaser 包体与校内网络加载）、非功能性测试。

### 5. 美术资源与版本管理

- 第一轮：版本 tag 管理、每周迭代纪要、GitHub 仓库维护。
- 第二轮：玩家雪碧图、地图建筑贴图生成与处理（沿用 `assets/characters/processed/` 规格管线）、视觉风格基准把控；兼任掉落表数值、任务文本等内容工作。
- 第三轮：文档回填（B-05 到 B-09 烟测记录、图导出复核记录）、开源许可证流程。
